# How tiny-crow is put together, release 1.8.5

Tiny Crow is a small coding agent written in TypeScript. It asks for Node.js 24 or later, and because it relies on type stripping, the files under `src/` execute directly as authored, with no compilation pass in between, while the files under `tests/` execute under the test runner that ships with Node itself.

## Guiding choices that shaped the code

The terminal interface is hand-built rather than borrowed from a widget library, so the project keeps its own line buffer, its own Markdown rendering, and its own scrolling and selection logic, and the whole interface stays self-contained with no runtime packages at all. A single provider layer sits in front of every model vendor, so agent logic never has to branch on which vendor is answering. Permission rules come in two flavours, a fast glob flavour and a richer regex flavour, and a watchdog notices when the same tool call repeats without progress. When the token count climbs toward the edge of the context window, older messages are condensed and dropped, leaving a short summary behind. Optional behaviour is switched on through settings or flags at run time, never through a separate build: worktrees, MCP, subagents, the architecture-note loader, status signals, and logging ride along by default, while the headless loop, ACP serving, persistent memory, the advisor, hooks, language servers, output filtering, multimodal input, and exporting are all toggled the same way. Hooks sit around tools rather than in place of the permission check, so a hook rewrite can only narrow a request; it can never widen a permission the checker would have refused.

## Launching, and the modes a launch can take

Every launch passes through one dispatch point, `main()` in `src/main.ts`, which reads the flags, loads settings, gathers context files, and restores a session, in that order. From there the program fans out: asking to print the resolved settings prints them and stops; `--acp` starts the ACP server; `--print` asks for one reply and stops; `--loop` runs the headless iterative loop; and with no mode flag at all, the interactive terminal interface opens. A previous session can be pulled back in first with `--resume`, `--continue`, or `--session <id>`, and further flags register the advisor tool, silence the hook dispatcher, dry-run one hook, or stream start, stop, and git-conflict notices over a Unix socket for an external status bar.

Once the interactive interface is running, its loop listens to several streams at once: keystrokes, mouse actions, resizes, and pastes arriving from the event thread; results of background agent prebuilding; streaming agent events; permission questions waiting for an answer; results from parallel `/btw` side questions; and a ticking refresh that keeps the spinner moving, pausing briefly when nothing else is ready. Typed text is handled by the input editor, a submitted line starts the agent runner, and the streamed events that come back are painted by the renderer and appended to the session.

## The journey of one request

A submitted line travels from the input editor's buffer into the agent runner together with the prompt and the conversation so far. The runner talks to the provider client, which calls the model vendor's API, and the reply arrives as a stream of agent events: tokens, reasoning fragments, tool calls, tool results, subagent tool calls, errors, and a final done marker. The event handler paints those events into the renderer's viewport buffer, which becomes terminal draw commands. A tool call first passes through the hook dispatcher's pre-tool stage, which may allow it, ask about it, deny it, or rewrite its arguments, and then through the permission checker's own verdict of allowed, ask, or denied; an ask pauses for the person at the keyboard to approve or refuse, while an allowed call runs one of the tools (shell, read, write, edit, search, and the rest) and then passes through the post-tool rewrite stage. When the done marker arrives, the session is appended and saved.

Sessions are written as JSON files under the data directory (the one named by `$TC_DATA_DIR`, or the operating system's data directory when that variable is absent), inside a folder suffixed with `tiny-crow`, under `sessions/`. The running chat history is appended to `chat_history.jsonl` in that same data directory. Log files land in `logs/` under names shaped like `tiny-crow-<timestamp>_<pid>.log`, and only appear when verbose logging or an explicit log file has been requested.

## The central types, and what each one owns

Resolved settings live in `Config`, and every runtime behaviour answers to it; command-line arguments live in `Cli` and take precedence over the matching settings fields. One provider layer fronts all vendors (OpenAI, Anthropic, Gemini, Ollama, OpenRouter) and the agent built on it offers a one-shot print mode plus the spawned streaming runner. Streaming output is modelled as `AgentEvent`, with variants for tokens, reasoning, tool calls, tool results, subagent tool calls, errors, and completion; terminal input is modelled as `UserEvent`, with variants for keys, scrolling in either direction, resizing, pasting, and mouse press, drag, and release. `Session` is the serialisable record of a conversation: its messages, its compactions, its costs, its permission allowlist, and its model and provider details. `PermissionChecker` holds the two-layer rules, the repeated-call detection, and the security-mode dispatch. `Renderer` owns the line-buffered viewport, the Markdown painting, and scrolling and selection, and every byte of terminal output flows through its backend; tests substitute a fake backend with fixed geometry that captures frames. `InputEditor` owns the text buffer, the cursor, the history, the kill ring, and picker integration. `ContextFiles` carries the loaded agent instructions, prompts, themes, and architecture notes. `HookDispatcher` merges pre-tool verdicts, letting the most severe win, and enforces post-tool and lifecycle decisions; it wraps each tool outside that tool's own permission check.

## Where each part of the program lives

The entry and flag definitions sit in `src/main.ts` and `src/cli.ts`. The model-vendor layer is `src/provider.ts`, and the place API keys are resolved from is `src/auth.ts`. Event shapes live in `src/event.ts`. The engine directory, `src/engine/`, holds the agent event loop, tool dispatch, and streaming. Agent construction, spawning, streaming, and subagent execution, together with system prompts and the tool set (read, write, edit, shell, grep, file search, directory listing, todo, plus the task and advisor tools), live under `src/agent/`. Session state, JSON file storage, and chat history live under `src/session/`. Safety lives under `src/permission/`: glob and regex rules with repeated-call detection, the user prompt interface, and pattern handling. The terminal interface lives under `src/ui/`: the event loop, the raw-mode guard, the renderer, the input editor and pickers, the status line, Markdown handling, the event handler, grouped interface state, and slash commands including the `/` picker. Context gathering lives under `src/context/`: embedded prompt themes and the loading of agent and architecture notes. Settings live under `src/config/`: loading from TOML, YAML, and JSON on disk plus the environment, and the types for quick models, custom providers, colours, and edit systems. Optional subsystems live under `src/extras/`: the headless loop, the MCP client, the ACP server, persistent memory, parallel task delegation, git worktrees, architecture-note handling, external-model consultation, image and PDF ingestion, lifecycle hooks with trust-hash confirmation, language servers, output filtering, prompt-chain transitions, and Unix-socket status signals. Around those sit `src/sandbox.ts` for wrapping shell commands with `bwrap` or `zerobox`, `src/fs.ts` for filesystem helpers, `src/pricing.ts` for token price constants, `src/startup.ts` for the phased start-up (settings, client, and context resolution, then optional-subsystem setup), `src/logging.ts` for structured logging, and `src/docs.ts` for the built-in documentation lookup behind the getting-started guide and `--tutor`.

## Proving a change before claiming it

Tests live under `tests/` as `*.test.ts` files and run with Node's built-in runner through `npm test`, which invokes `node --test` over the test files and the hooks tests. Type safety is a separate pass, `npm run typecheck`, which runs `tsc --noEmit`. Neither pass alone is enough to call a change good; both have to pass. Headless main-loop tests exercise the real terminal loop with no terminal and no network, painting into a fake backend and feeding scripted user events, while agent runs use a mock completion model.

## What the program is built from

There are no packages needed at run time. Development tooling is limited to `typescript` for type checking with `tsc --noEmit` and `@types/node` for the Node.js type definitions. Everything else comes from Node.js built-ins: `node:fs`, `node:child_process`, `node:readline`, `node:http(s)` for vendor API calls, and `node:test` for the suite. Settings are parsed from TOML, YAML, or JSON, and sessions are serialised as JSON.
